# Live call (Presence)

Transport: Lovable AI Gateway Live, model `openai/gpt-live-1`, endpoint `wss://ai.gateway.lovable.dev/v1/live/sessions`.
Browser ↔ `/api/live` (app relay, `src/lib/live/live-relay.server.ts`) ↔ Gateway carry SDP, heartbeats and transcript events; audio is WebRTC browser ↔ provider. Server-only `LOVABLE_API_KEY`; no external account, card or key. Billed per second from the workspace's Lovable credits (15 s minimum per call). Retention: Cocoon stores no audio or transcripts. The authenticated model catalog lists `data_retention: zero` for the live surface, but that is catalog metadata, not a contractual guarantee, and Lovable's AI app-context logging (docs.lovable.dev/features/ai) may retain requests; the UI therefore only promises that Cocoon does not save them and that Lovable/provider policies apply.

Controls: verified sign-in (token sent in the first socket message, checked server-side), `reserve_voice` quota (1 concurrent, 3/hour, 10/day), server hard stop at 5 minutes, owner pause via `production_service_state` service `live-voice`, three explicit acknowledgements (roleplay, audio, age 18+ or guardian permission). No transcript storage; captions are in-memory only. No tools: delegations are answered locally without extra model calls. The persona may say agreed pretend lines ("I'm waiting for you") but is instructed never to claim observation, tracking, physical help or contacting anyone.

Failure: explicit error plus a user-initiated `tel:` handoff to Safety Kit contacts. The scripted browser demo is collapsed and never an automatic fallback.

Not verified: real microphone/audio, voice quality, latency and Hinglish delivery — no live call was made during development. Direct OpenAI (`naturalVoice`), Twilio and Gemini policies stay OFF.

## Signed-out demo calls
Visitors without an account can request a real GPT-Live demo call after explicit consents and microphone permission. The browser sends an empty token; the relay hashes the trusted server-provided client IP (SHA-256, raw address never stored) and reserves a slot via `reserve_guest_voice`: one open call per network/IP, 2/hour and 4/day per network/IP, 60/day and 5 concurrent globally. Shared networks may share these limits. No fingerprinting or browser-supplied identity is used; a missing trusted IP refuses guest startup. Demo calls are cut off after 2 minutes server-side. Pausing `live-voice` in `production_service_state` stops new demo calls too; lookup errors or missing control state fail closed before reservation/provider traffic. Real microphone/audio remains untested.

## Verification log (Oct 2026)
- Root cause of "Live voice limits could not be checked": the hosted `production_service_state` had no `live-voice` row, so the fail-closed check refused every call. Migration 0011 inserts it unpaused with `ON CONFLICT DO NOTHING` (an owner pause is never overwritten); `live-control-seed.test.ts` executes it in PGlite.
- One bounded synthetic smoke call on the published site (headless Chromium, fake audio device, signed-out, fictional default context): WebSocket upgrade → `app.start` → `gateway.session.created` (SDP answer) → `session.started` → remote track, then `initial_heartbeat_timeout` and `session.closed` with `usage.seconds=15`, socket closed 1000, slot released. Media never connected because the sandbox browsers (Chromium and Firefox) gather zero ICE candidates, even though UDP to STUN works from the host — an environment limit, not evidence about real users.
- The hook now refuses to open a paid session when the offer has no ICE candidates, and waits up to 10 s for gathering (proceeding early once a public STUN route exists).
- Still unverified: WebRTC connection, heartbeats, opening greeting audio, barge-in and End on a real browser/network. Verify with one real call on a normal network.
